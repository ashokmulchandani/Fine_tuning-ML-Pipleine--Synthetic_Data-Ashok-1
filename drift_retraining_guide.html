Drift Retraining — When & How to Retrain

Drift detected? New Q&A from users? Yes, you can append and retrain — but with three critical guardrails. The drift alert tells you SOMETHING changed. A human decides WHAT to do about it.

1. The Happy Path — Yes, It Works

🔴 Drift detected → 50% of queries about Kubernetes
  → Generate 500 new Q&A pairs about Kubernetes
  → Append to instruction_data.json
  → dvc add + dvc repro
  → Model now handles Kubernetes + Metformin ✅

DVC sees the new data hash, dvc repro re-runs the pipeline.
MLflow logs the new run. Evidently confirms drift resolved.
This works mechanically. But three things can go wrong…

2. Guardrail 1 — Catastrophic Forgetting

If your new data is 500 Kubernetes Q&A and your old data is only 50 medical Q&A, the model forgets Metformin entirely.

Before retrain:
"What is Metformin?"
→ "Biguanide for diabetes..." ✅
After retrain:
"What is Metformin?"
→ "I think it's a K8s pod?" ❌
✅ Fix: Mix old + new data. The training set should be original_qa.json + new_qa.json, not just new_qa.json. DVC append keeps everything together.

3. Guardrail 2 — LoRA Adapter Stacking

You cannot train a second LoRA on new data and stack it on top of the old one.

❌ WRONG:
model = PeftModel.from_pretrained(base, "adapter_v1") # Medical
model = get_peft_model(model, lora_config) # K8s adapter
→ Two unmerged adapters = undefined behavior
✅ RIGHT:
model = PeftModel.from_pretrained(base, "adapter_v1")
model = model.merge_and_unload() # Bake in medical
model = get_peft_model(model, lora_config) # Fresh LoRA
trainer.train() # Medical + K8s together
✅ Merge before retraining. merge_and_unload() bakes B×A into W₀, producing a standard model. Apply fresh LoRA. Train on combined dataset.

4. Guardrail 3 — Not All Drift Needs Retraining

Drift TypeExampleAction
New vocabulary, same topic"K8s" instead of "Kubernetes"❌ Don't retrain — add synonym mapping
New topic, same domain"Docker" added to DevOps questions✅ Retrain with appended data
Completely new domainMedical → Cooking questions⚠️ Fine-tune a SEPARATE model, don't mix
Seasonal driftTax questions appear in April⏰ Schedule retraining, don't react daily

5. Where Do New Q&A Pairs Come From?

The Q&A pairs must come from somewhere real — you cannot just invent Kubernetes facts.

SourceQualityCostHow
🥇 Business source docsHighestFreePhase 4 pipeline: PDF → extract → chunk → format. K8s runbook → Q&A. Docs already exist.

6. The Actual Flow — What We Built

check_drift.py runs daily (GitHub Actions 6am UTC)
  │
  ├── drift < 0.5 → Nothing happens. Model is healthy. 🟢
  │
  └── drift > 0.5 → Alert fires 🔴
        │
        ├── Human reviews: WHAT drifted?
        │   "Users are asking about Docker and Kubernetes now"
        │
        ├── Collect/generate new Q&A for Docker + K8s
        │   → Append to instruction_data.json
        │   → dvc add data/instruction_data.json
        │   → dvc push (new version tracked!)
        │
        ├── dvc repro (re-runs prepare → train → evaluate)
        │   ├── prepare_data: validates old + new data together
        │   ├── train: merges old adapter, trains on combined dataset
        │   │   └── MLflow: "run #7: 600 examples, final_loss=0.28"
        │   └── evaluate: MFT checks Metformin still works ✅
        │           DIR checks Kubernetes safety ✅
        │           Drift check: now 0.15 (in-distribution!) 🟢
        │
        └── Promote to Production (MLflow)
            mlflow models transition medical-qa 7 --stage Production

Old adapter (v6, medical only) → Archived
New adapter (v7, medical + DevOps) → Production ✅
🔑 The key insight: It is not automatic. The drift alert tells you SOMETHING changed. A human decides WHAT to do about it. The pipeline makes the retraining reproducible and verifiable. You never retrain blindly on drift alone.
📁 Full pipeline: check_drift.py → dvc add → dvc repro → train_stage.py → evaluate_stage.py → mlflow promote. All automated in CI/CD. on drift alone.
